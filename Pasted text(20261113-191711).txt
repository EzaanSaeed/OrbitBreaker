# PART 1 — GAME OVERVIEW

## 1.1 Game Title

**Orbit Breaker**

The title was selected after exploring an earlier concept called *Cosmic Control*.

Orbit Breaker is the current game and should be treated as the official project title.

**Status: Finalized**

## 1.2 Game Concept

Orbit Breaker is a **2D side-scrolling endless space survival game** in which the player controls a spaceship flying through a procedurally continuing environment filled with planets and potentially other obstacles.

The spaceship automatically progresses through space.

The player does not directly control its forward movement. Instead, the player uses upward and downward thrusters to maintain a safe trajectory.

The central gameplay mechanic is **planetary gravity**.

As the spaceship approaches planets, their gravitational attraction pulls it toward them. The player must compensate for these forces while navigating the environment.

The objective is to survive as long as possible and travel the greatest possible distance.

As the game continues, movement speed increases, making survival more difficult.

The intended experience combines the accessible controls of an endless runner with a space-themed physics challenge.

### One-sentence pitch

> Orbit Breaker is a 2D endless space runner where players use spaceship thrusters to fight planetary gravity, avoid collisions, and survive an increasingly dangerous journey through the cosmos.

## 1.3 Genre

**Primary genre:** Endless runner  
**Secondary elements:** Arcade survival, physics-based navigation

The game is not currently a puzzle game, a spaceship combat game, or an orbital simulation.

### Inspiration

The team explicitly referenced **Subway Surfers** as an example of endless-runner progression.

However, Orbit Breaker differs from a lane-based runner:

- The player navigates vertically rather than switching fixed lanes.
- Planets influence movement through gravitational attraction.
- Obstacles move relative to the spaceship as the environment scrolls.
- Survival depends partly on managing momentum and gravity.

The goal is a simple-to-understand game with a distinctive physics mechanic.

## 1.4 Game Jam Theme

**Theme: COSMOS**

The game uses this theme through its setting and mechanics:

- Outer-space environment
- Spaceship protagonist
- Planets
- Gravitational forces
- Space navigation
- Potential asteroids and other celestial hazards

The gravitational mechanic is intended to make the theme relevant to actual gameplay rather than merely providing a space-themed background.

**Status: Finalized**

## 1.6 Intended Player Experience

The game should initially feel manageable, then become increasingly challenging.

A typical play session should involve:

1. The spaceship begins flying forward automatically.
2. The environment moves toward the player.
3. A planet appears ahead.
4. Its gravity begins influencing the spaceship.
5. The player uses thrusters to maintain a safe trajectory.
6. The player avoids the planet and continues traveling.
7. The distance score increases.
8. New planets appear and the game accelerates.
9. Eventually, a collision or boundary violation ends the run.
10. The player restarts to attempt a better score.

The design prioritizes replayability through a straightforward survival loop.

## 1.7 Camera and Movement Model

The original implementation proposal uses a fixed horizontal player position.

For a 960×540 game window, the spaceship begins approximately at:

- X = 180
- Y = 270

The world scrolls from right to left.

Planets spawn offscreen on the right, move left, and disappear after passing the player.

The player's primary movement is vertical.

This produces the appearance of forward travel without requiring the spaceship to physically move across a large world.

**Status:** Planned MVP design.

### Important physics distinction

The proposed gravity implementation affects **vertical acceleration only**.

This is an intentional simplification for an endless runner.

It is not a full two-dimensional orbital simulation, even though the game uses concepts inspired by planetary gravity.

Full orbital motion and gravitational slingshot mechanics were considered in an earlier version of the concept, but are not required for the current MVP.

## 1.9 Core Gameplay Mechanics

### A. Automatic forward progression

The environment moves left at a speed that represents the spaceship's forward progress.

The spaceship remains near a fixed horizontal coordinate.

### B. Vertical thruster control

Pressing Up/W accelerates the spaceship upward.

Pressing Down/S accelerates it downward.

Movement is intended to involve acceleration and velocity rather than only instant position changes.

### C. Planetary gravity

Planets exert gravitational attraction on the spaceship.

The closer the spaceship is to a planet, the greater the intended effect of gravity.

A planet above the ship tends to pull it upward.

A planet below the ship tends to pull it downward.

The initial implementation simplifies gravity to a vertical acceleration value.

### D. Momentum

The spaceship maintains vertical velocity over time.

Releasing the movement keys does not necessarily stop the ship immediately.

Gravity and thrust both influence its resulting motion.

### E. Planet collision

If the spaceship collides with a planet, the run ends.

### F. Screen boundaries

If the spaceship leaves the permitted vertical play area, the run ends.

### G. Endless procedural spawning

Planets continue appearing ahead of the spaceship.

The initial system uses randomized vertical positions and repeating spawn intervals.

### H. Distance score

The game tracks how far the spaceship has traveled.

Score increases as the world scrolls.

### I. Increasing difficulty

The original plan increases world scrolling speed over time.

The exact difficulty curve is subject to playtesting.

### J. Restarting

After game over, the player can begin a fresh run.

These are the core mechanics needed before optional features are considered.

## 1.10 Progression and Difficulty

Orbit Breaker is intended to be an endless game rather than a series of traditional levels.

There is no predetermined final level in the MVP.

The current plan is to increase difficulty by raising the scrolling speed as distance increases.

An earlier code example suggested:

- Initial scrolling speed: 180 pixels/second
- Maximum scrolling speed: 350 pixels/second
- Speed increases based on accumulated distance

These are **prototype tuning values**, not approved final balance parameters.

Other possible methods of increasing difficulty include:

- Shortening the delay between planets
- Increasing gravitational strength
- Changing planet sizes
- Introducing more complex obstacle patterns
- Adding asteroids

Those additions have not been finalized.

## 1.11 Win and Loss Conditions

### Winning

There is no traditional win condition in the current endless-runner design.

The objective is to survive and achieve a high distance score.

### Losing

The run ends when:

- The spaceship collides with a planet.
- The spaceship exits the vertical play area.

Collision with other hazards would also end the run if those hazards are eventually implemented.

### High scores

Beating a previous high score has been described as part of the intended replay experience.

However, persistent high-score saving has not been designed or implemented.

Whether scores persist across browser sessions is **not yet decided**.

## 2.4 Software Architecture Decision

The team compared **MVC** and **N-tier**.

The recommendation was to use:

**Scene-based, component-oriented Godot architecture with lightweight separation of concerns inspired by MVC.**

Reasoning:

- Godot already organizes games around scenes and nodes.
- The game does not need a traditional multi-tier application backend.
- Strict MVC would introduce unnecessary boilerplate.
- Independent scene ownership helps collaborative development.
- Two developers can build separate systems and integrate them later.

This is the currently recommended architecture, but the exact class design remains open pending Developer B's domain model.

# PART 5 — SOFTWARE ARCHITECTURE

## 5.1 Recommended Architectural Approach

Use **Godot's scene-based architecture with component-oriented separation of concerns**.

Keep the design lightweight.

The intended separation is:

- Player handles spaceship behavior.
- Planet provides planet-specific properties and gravitational influence.
- Main coordinates world simulation and overall game state.
- HUD handles presentation and player-facing controls.

This organization is loosely inspired by MVC, but it is not strict MVC.

The final domain model may refine these responsibilities.

Owns:

### `hud.gd`

Owns:

The HUD should not directly calculate gravity or spawn planets.

## 5.8 Proposed Gravity Interface

The original architecture used the planet to calculate gravitational acceleration.

A proposed interface is:

```gdscript
func get_gravity_at(ship_position: Vector2) -> float:
    # Return vertical gravitational acceleration.
    pass
```

The player exposes:

```gdscript
func apply_gravity(amount: float) -> void:
    # Receive a gravity contribution.
    pass
```

The main scene coordinates them.

Conceptually:

```text
Planet calculates gravity
          |
          v
Main collects gravity values
          |
          v
Player receives gravity
          |
          v
Player updates vertical velocity
          |
          v
Player changes vertical position
```

### Example mathematical model

Let:

```text
direction = planet_position - player_position

distance_squared = max(
    length_squared(direction),
    minimum_distance_squared
)

gravity_magnitude =
    gravity_strength / distance_squared

vertical_gravity =
    normalized(direction).y * gravity_magnitude
```

The result is a signed vertical acceleration.

This represents an inverse-square-style force approximation.

It does not simulate full two-dimensional orbital mechanics.

## 5.9 Previously Suggested Physics Parameters

These values appeared in earlier example scripts.

They are **starting points for experimentation, not finalized gameplay balance**.

| Parameter | Suggested value |
|---|---|
| Player thrust power | 650 |
| Player gravity multiplier | 1.0 |
| Maximum vertical speed | 350 |
| Planet gravity strength | 350,000 |
| Minimum gravity distance squared | 2,500 |
| Player collision radius | 12 |
| Planet radius | 35 |
| Initial scroll speed | 180 |
| Maximum scroll speed | 350 |
| Planet spawn interval | 3 seconds |
| Planet spawn X | 1050 |
| Planet spawn Y | Random from 90 to 450 |
| Planet cleanup threshold | X less than -100 |
| Player initial position | (180, 270) |
| Proposed viewport | 960×540 |

### Tuning warning

At a distance of approximately 100 pixels, gravity strength 350,000 produces a force magnitude of approximately 35 pixels/second² before considering direction.

That may feel weak relative to a thrust power of 650.

The game should be balanced through testing rather than treating the initial numbers as authoritative.

## 5.10 Physics Update Ordering

An important technical issue was identified in the original prototype plan.

The planet gravity must be applied before the player performs its physics update and clears its accumulated gravitational acceleration.

The earlier recommendation was to set the main controller's physics process priority to `-1`, allowing it to apply gravity before the player updates at the default priority.

An alternative is to coordinate both calculations explicitly from one physics update sequence.

This ordering must be handled deliberately.

Otherwise, gravity might be delayed, overwritten, or behave inconsistently.

## 5.11 Proposed Scrolling and Spawning Logic

The previous example used these concepts:

```text
Every physics frame:

    if game is over:
        stop updating gameplay

    move all planets left

    remove planets that moved offscreen

    compute gravitational acceleration

    apply gravity to player

    update spawn timer

    if spawn interval reached:
        spawn a planet

    increase traveled distance

    increase scrolling speed

    check collisions and boundaries

    update HUD
```

The exact order should be adjusted for correct physics and collision behavior.

The main requirement is predictable gameplay, not adherence to a particular loop structure.

## 5.12 Collision Handling

Two possible approaches have been discussed or implied.

### Option A — Manual distance checking

Compare the distance between the player's center and a planet's center.

A collision occurs when:

```text
distance < planet_radius + player_radius
```

This matches the earlier example.

It is simple for circular obstacles.

### Option B — Godot Area2D collision signals

Use properly configured `Area2D` collision layers and masks.

Detect overlap through signals.

This more directly uses Godot's collision system.

**Status: Not yet decided**

Whichever approach is chosen, avoid running two independent collision systems that produce duplicate death events.

The domain model review may help identify the cleanest ownership.

## 5.13 Game State Management

The current prototype concept requires at least two logical game states:

```text
RUNNING
GAME_OVER
```

A future design could also include:

```text
READY
PAUSED
```

But those are optional.

A minimal controller can use a Boolean such as `game_over`.

A more structured implementation could use an enum:

```gdscript
enum GameState {
    RUNNING,
    GAME_OVER
}
```

Neither is yet the finalized implementation.

The key requirement is consistent state transitions.

When the player dies:

1. Mark the run as ended.
2. Stop player control and gameplay progression.
3. Stop increasing score.
4. Display the final score.
5. Display the game-over UI.
6. Enable restart.

When restarting, gameplay should reset to its initial state.

The original example used:

```gdscript
get_tree().reload_current_scene()
```

This is a reasonable MVP restart method.

## 5.14 Signals and Communication

Godot signals are recommended for communication between independent scenes.

Potential signals include:

```gdscript
signal player_died
signal score_changed(score: int)
signal restart_requested
signal game_over(score: int)
```

These are **proposed API names**, not previously finalized interfaces.

Suggested ownership:

| Event | Emitter | Receiver |
|---|---|---|
| Player death | Player | Main |
| Score change | Main | HUD |
| Game over | Main | HUD |
| Restart request | HUD | Main |

The final design might use direct methods for simple interactions instead.

For example:

```gdscript
hud.update_score(score)
```

Both approaches are valid.

The important principle is that the HUD does not control world physics and the player does not directly manage UI widgets.

## 5.15 Reusable Configuration Data

The game may eventually benefit from external configuration values.

Examples:

- Thruster strength
- Gravity multiplier
- Planet gravity strength
- Minimum spawn interval
- Maximum scrolling speed
- Planet radius

Godot's exported script variables are enough for the MVP.

Custom `Resource` types could be used later if there is a genuine need for reusable configuration objects.

Avoid creating many abstract classes solely for architectural appearance.

## 5.16 Integration Contract Between Developers

Before parallel implementation, agree on a small shared interface.

### Proposed Player contract

```text

    apply_gravity(amount: float)
    emits player_died
```

### Proposed Planet contract

```text

    get_gravity_at(player_position: Vector2) -> float
    exposes radius
```

### Proposed HUD contract

```text

    update_score(score: int)
    show_game_over(score: int)

```

### Proposed Main contract

```text

    creates/owns game world

    manages restart
```

These interfaces should be reviewed against Developer B's domain model before being treated as permanent.

# PART 6 — DOMAIN MODEL INTEGRATION

## 6.1 Critical Context

Developer B is independently designing a domain model for Orbit Breaker.

**That model has not yet been provided or reviewed.**

The following section describes what the model should address, not what it already contains.

Do not assume class names, inheritance structures, diagrams, or relationships from an unseen model.

The actual model must be examined when Developer B supplies it.

## 6.2 Purpose of the Domain Model

The domain model should describe the important concepts within the game, their responsibilities, and the relationships between them.

It should help clarify questions such as:

- What is a player?
- What is a planet?
- Where does gravitational behavior belong?
- Who manages game progression?
- What constitutes a collision?
- What information represents the current run?
- How are game events communicated?
- Which responsibilities should be independent?

The domain model should reflect the agreed gameplay rather than introduce unrelated features.

## 6.3 Candidate Domain Concepts

The following are **candidate concepts derived from gameplay requirements**, not a finalized UML model.

### Player or Spaceship

Potential responsibilities:

- Position
- Velocity
- Thruster input
- Gravity response
- Collision state
- Alive/dead state

### Planet

Potential responsibilities:

- Position
- Radius
- Gravity strength
- Collision geometry
- Visual properties

### Game Session or Game Controller

Potential responsibilities:

- Current run status
- Distance traveled
- Difficulty level
- Start and end conditions
- Restart behavior

### World or Environment

Potential responsibilities:

- Active celestial objects
- World scrolling
- Object cleanup
- Spawn management

### Spawner

Potential responsibilities:

- Spawn interval
- Spawn positions
- Difficulty-aware generation

A separate Spawner class is optional.

### Score

Potential responsibilities:

- Current distance
- Final score
- High score, if approved

Score may be a simple numeric property rather than a dedicated class.

### HUD

Potential responsibilities:

- Score presentation
- Game-over presentation
- Restart interaction

The HUD is primarily a presentation component rather than a core physics entity.

### Gravity behavior

Potential responsibilities:

- Calculate gravitational influence
- Apply gravitational influence

This may be implemented as planet behavior, a reusable component, or another service.

No choice has been finalized.

## 6.4 Important Relationships to Consider

A proposed model should clarify:

- One game session manages the active run.
- The world contains dynamically spawned planets.
- The player is affected by gravity from nearby planets.
- Planets can act as collision hazards.
- The game controller manages the active score.
- The HUD displays game state and score.
- Restart creates a fresh run or resets the relevant systems.

Be careful when choosing inheritance versus composition.

For example, the domain model should not automatically make Player inherit from Planet merely because both have positions.

They may share certain properties without representing the same domain concept.

## 6.5 Decisions That Must Remain Flexible

Until the model has been reviewed, do not finalize:

- A complete class hierarchy
- All inheritance relationships
- A dedicated physics manager
- A separate world manager
- A global autoload singleton
- A custom state machine framework
- A generic obstacle base class
- A separate score class
- A centralized event bus
- Numerous reusable Resource types

Some of these may be useful, but the MVP does not automatically require them.

## 6.6 How Developer B's AI Should Evaluate the Model

When the model is supplied:

### Step 1 — Explain the existing model

Identify:

- Classes or entities
- Attributes
- Methods
- Relationships
- Association multiplicities
- Inheritance
- Composition
- Dependencies

Explain what the diagram or written model actually says.

Do not silently correct it before explaining it.

### Step 2 — Compare the model with gameplay requirements

Check whether it supports:

- Vertical thruster input
- Player velocity
- Gravity influence
- Planet spawning
- World scrolling
- Collision handling
- Distance scoring
- Difficulty progression
- Game-over state
- Restart functionality
- HUD updates

Identify requirements that have no obvious owner.

### Step 3 — Evaluate responsibility allocation

Look for:

- Excessively large classes
- Duplicate responsibilities
- Unnecessary coupling
- Circular dependencies
- Unclear ownership
- UI logic inside physics systems
- Spawning logic inside the Player
- World logic duplicated between Main and another manager

### Step 4 — Evaluate complexity

Determine whether the design is practical for a small Godot game.

A well-designed model should be sufficiently structured to support teamwork but simple enough to implement during a game jam.

Do not recommend architectural complexity without a clear benefit.

### Step 5 — Recommend changes

For each proposed change, explain:

- What should change
- Why it should change
- Which requirement it supports
- Which files or responsibilities it affects
- Whether it changes any agreed gameplay behavior

### Step 6 — Obtain agreement on architectural changes

Recommendations that materially affect the shared architecture must be discussed with Developer A.

Do not treat a new suggestion as an approved requirement merely because Developer B's AI proposed it.

## 6.7 Translating the Model into Godot

Not every UML class must become a Godot scene.

The correct implementation depends on the class's responsibility.

| Domain concept | Possible Godot implementation |
|---|---|
| Player | `Area2D` scene with GDScript |
| Planet | `Area2D` scene with GDScript |
| Game controller | `Node2D` or `Node` with script |
| HUD | `CanvasLayer` with Control nodes |
| Spawner | Script or dedicated Node |
| Game configuration | Exported properties or Resource |
| Score | Property of the game controller, or dedicated data object |
| Gravity calculation | Planet method, component, or helper |

These mappings are starting recommendations.

They are not mandatory final class definitions.

## 6.8 Domain Model Conflict Resolution

Suppose the supplied model suggests a mechanic or design that differs from the established game.

The AI should classify the difference:

### Type A — Implementation-only difference

Example: The model uses a separate `GravitySystem` instead of having planets calculate gravity.

This could be acceptable if the gameplay remains unchanged.

### Type B — Scope expansion

Example: The model adds fuel management.

Fuel was previously discussed only as an optional feature.

It should not automatically become required.

### Type C — Gameplay contradiction

Example: The model makes the player manually control horizontal spaceship movement through full orbital simulation.

This conflicts with the agreed endless-runner MVP.

The AI should identify the conflict and request a deliberate team decision.

### Type D — Missing requirement

Example: The model has planets and a player but no apparent owner for scoring or game-over state.

The AI should recommend where that responsibility belongs.

## 6.9 Expected Domain Model Review Output

Developer B's AI should produce:

1. An explanation of the supplied domain model.
2. A requirements coverage assessment.
3. A list of strengths.
4. A list of missing or questionable elements.
5. Proposed revisions.
6. A revised model, if useful.
7. A Godot implementation mapping.
8. A Developer B file ownership list.
9. Integration contracts with Developer A.
10. A development sequence.

The approved model should then become part of the shared project documentation.

Do not casually delete or rewrite shared project configuration.

Godot resource identifiers and scene references should be preserved unless there is a clear reason to change them.
